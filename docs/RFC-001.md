# RFC-001 — Network Inventory and Automation Pipeline

## Status

- State: Draft
- Date: 2026-05-01
- Scope: Production network inventory and automation platform

SCI authority note:

- RFC-001 is subordinate to SYSTEM_CONTRACT_INDEX.md.
- If RFC-001 conflicts with SCI, SCI is authoritative and RFC-001 is descriptive for conflicting scope.

## 1. Problem Statement

The platform currently relies on discovery inputs that can diverge from future control-plane intent. Inventory consistency must be enforced across an active discovery pipeline and a future source-of-truth platform.

Primary issues:

1. Inconsistent network inventory across LogicMonitor and future Nautobot.
2. Need for a validated, scalable, multi-vendor network state system.

## 2. Goals

1. Build a validated inventory pipeline with deterministic processing.
2. Support 1000+ devices across in-scope vendors.
3. Enable future automation safely through staged controls and explicit guardrails.

## 3. Non-goals

1. No immediate configuration deployment.
2. No SDN abstraction layer in this phase.
3. No reliance on LogicMonitor as source of truth.

## 4. System Architecture

### 4.1 Pipeline A (Active): Discovery + Validation

Flow:
LogicMonitor -> Python ingestion -> Normalized inventory -> Ansible validation -> PostgreSQL API

### 4.2 Pipeline B (Future): Control Plane

Flow:
Nautobot -> Ansible -> Network devices

### 4.3 High-Level Diagram

```text
PIPELINE A (ACTIVE)

[LogicMonitor]
    |
    | discovery data (non-authoritative)
    v
[Python Ingestion]
    |
    | normalized records
    v
[Normalized Inventory]
    |
    | validation targets
    v
[Ansible Validation]
    |
    | evidence + status
    v
[PostgreSQL API]


PIPELINE B (FUTURE)

[Nautobot]
    |
    | desired state intent
    v
[Ansible Execution]
    |
    | approved actions only
    v
[Network Devices]
```

### 4.4 Layer Responsibilities

1. Discovery layer (LogicMonitor): collect observations only.
2. Ingestion layer (Python): normalize and quality-check incoming data.
3. Inventory layer: provide canonical records keyed by IP.
4. Execution layer (Ansible): run validation now; run controlled changes only after explicit enablement.
5. Persistence layer (PostgreSQL API): store canonical state, validation outcomes, and audit evidence.
6. Control-plane layer (Nautobot): future desired-state authority after formal cutover.

Mandatory authority constraints:

- LogicMonitor is discovery-only and not authoritative.
- Nautobot is future source of truth and is not yet authoritative.
- Ansible is execution-only and never inventory authority.

## 5. Identity Rules

1. `ip_address` is the primary key across pipelines.
2. `hostname` is an attribute only and MUST NOT be used as primary identity.
3. `serial_number` is authoritative hardware identity metadata when available and validated.
4. `serial_number` MUST NOT replace `ip_address` as the pipeline primary key.
5. Records missing valid `ip_address` are invalid for targeting and execution.

## 6. Data Lifecycle

Lifecycle sequence:

ingestion -> normalization -> validation -> persistence

Processing requirements:

1. Ingestion accepts discovery payloads and applies schema checks.
2. Normalization maps vendor data to a canonical schema keyed by `ip_address`.
3. Validation executes read-only checks and collects evidence.
4. Persistence stores canonical records, run metadata, and validation outcomes through PostgreSQL API.

## 7. Failure Handling Model

Failure strategy is continue-on-failure.

Requirements:

1. The pipeline MUST continue processing remaining targets when one target fails.
2. Failures MUST be logged with error class, source stage, target IP, and timestamp.
3. Failures MUST be persisted via PostgreSQL API for audit and retry workflows.
4. The orchestrator MUST never stop overall pipeline execution due to individual target failure.
5. Pipeline completion status MUST include success, partial failure, and failed target counts.

## 8. Storage Model

1. Canonical state and execution evidence are stored in PostgreSQL via API.
2. Baseline retention policy is 30 days for operational records.
3. Each managed entity MUST maintain `last_seen` tracking for recency and stale-detection logic.
4. Storage writes MUST be idempotent for reruns of the same target in the same processing window.

## 9. Vendor Scope

Priority order:

1. Aruba (highest)
2. Cisco
3. Fortinet
4. Juniper
5. Meraki

All vendor adapters MUST conform to common identity, validation, and persistence contracts.

## 10. Execution Modes

Only these globally valid execution modes are defined by SCI:

### 10.1 READ_ONLY

- Discovery and validation allowed.
- No configuration mutation.

### 10.2 VALIDATION_ONLY

- Ansible read-only validation allowed.
- No mutation permitted.

### 10.3 CHANGE_ENABLED

- Configuration mutation allowed only when global guard is open and SCI permit is present.

If execution mode is undefined, default is READ_ONLY.

## 11. Future Migration Path to Nautobot

Migration is phased and gated.

Phase 1: Parallel operation

1. Keep PostgreSQL authoritative for canonical validated runtime state until SCI-approved cutover.
2. Ingest and map Nautobot data in parallel for reconciliation checks.

Phase 2: Reconciliation hardening

1. Validate schema parity and field-level ownership.
2. Resolve drift using deterministic precedence rules.
3. Confirm guardrails and rollback path under controlled tests.

Phase 3: Controlled authority cutover

1. Approve cutover through formal change control.
2. Set Nautobot as desired-state authority for Pipeline B.
3. Keep rollback capability to PostgreSQL-led canonical mode until stabilization criteria are met.

Phase 4: Post-cutover monitoring

1. Track drift, run success rate, and stale records.
2. Enforce policy compliance and audit completeness.
3. Revert authority if critical thresholds are violated.
